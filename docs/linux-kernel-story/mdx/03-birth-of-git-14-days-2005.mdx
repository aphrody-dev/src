# The Birth of Git: 14 Days That Changed Source Code Management (2005)

## 1. The Pre-Git Era: Tarballs, Patches, and BitKeeper (1991–2005)

From 1991 to 2002, the Linux kernel was maintained primarily via:
- Compressed source tarballs released on `kernel.org`.
- Patch files sent across the Linux Kernel Mailing List (`LKML`).
- Linus Torvalds personally reading patches, evaluating diffs, and applying them using Larry Wall's `patch` utility.

By 2002, the sheer volume of contributors broke this manual workflow. Linux was receiving hundreds of patches per day from IBM, Intel, Red Hat, SUSE, and independent hackers. Centralized systems of the era—CVS and Subversion (SVN)—were fundamentally flawed for kernel development:
- **Centralized Lock-in**: Commits required an active network connection to a central master server.
- **Branching and Merging Disaster**: Branching was slow; merging branches in CVS often resulted in corrupted trees.
- **Zero Scalability**: An operation like checking file history or switching branches across 15,000 files took minutes.

Linus adopted **BitKeeper**, a proprietary distributed version control system developed by Larry McVoy's company, BitMover. BitMover granted free licenses to Linux kernel developers under specific terms: developers could not reverse-engineer BitKeeper or develop competing version control systems while using the free license.

## 2. The 2005 Crisis: Andrew Tridgell and License Revocation

In early 2005, Andrew "Tridge" Tridgell (famous creator of Samba) analyzed the network protocol of the BitKeeper client by connecting to the BitKeeper port using `telnet` and reading the help documentation and text streams, in order to write an open-source interoperability tool (`sourcepuller`).

Larry McVoy claimed this violated the reverse-engineering clause of the BitKeeper license. In April 2005, BitMover announced the termination of free BitKeeper licenses for Linux kernel development.

The Linux kernel was left without a version control system. Existing open-source alternatives were evaluated:
- **Subversion**: Centralized, slow, branching was broken.
- **CVS**: Obsolete, lacked atomic commits.
- **Monotone**: Distributed and cryptographically sound, but took over 30 seconds to apply a single patch, completely non-viable for a tree with 25,000 commits.
- **Arch**: Complex, poor ergonomics.

Linus famously declared:
> *"I can write a better version control system in two weeks than anything that currently exists."*

## 3. Linus's Design Principles for Git

Linus isolated himself in his home office in Beaverton, Oregon, in early April 2005. He set three non-negotiable architectural mandates:

1. **Distributed by Nature**: Every developer holds the entire history of the project locally. Commits, branch creation, checkouts, and logs must require zero network connectivity.
2. **Cryptographic Content-Addressable Storage**: History must be strictly immutable and tamper-proof. The data structure must be a Directed Acyclic Graph (DAG) keyed by SHA-1 hashes of the content.
3. **Speed Above All Else**: Applying a patch must take milliseconds. Switching branches across 20,000 files must take under a second, leveraging the operating system's buffer cache and memory-mapped files (`mmap`).

## 5. Architectural Deep-Dive: The Object Database and DAG

Git is not a delta-based version control system; it is a **content-addressable filesystem** with a VCS user interface layered on top.

```
       Commit Object in Git (40-hex SHA-1)
       +---------------------------------------------+
       | tree: e12b...                               |
       | parent: 7a8f... (omitted in root commit)    |
       | author: Linus Torvalds <torvalds@...>       |
       | committer: Linus Torvalds                   |
       |                                             |
       | "Commit message explaining the change"      |
       +---------------------------------------------+
                            |
                            v
       Tree Object (Directory representation)
       +---------------------------------------------+
       | 100644 blob 3b18...    Makefile             |
       | 040000 tree d42f...    kernel/              |
       | 040000 tree a981...    mm/                  |
       +---------------------------------------------+
                                   |
                                   v
              Tree Object for mm/
              +---------------------------------------------+
              | 100644 blob f90a...    memory.c             |
              | 100644 blob 1c5e...    page_alloc.c         |
              +---------------------------------------------+
                                          |
                                          v
                         Blob Object (File Content)
                         +-----------------------------------+
                         | zlib_deflate("/*                  |
                         |  * linux/mm/page_alloc.c          |
                         |  ...")                            |
                         +-----------------------------------+
```

### 5.1 The Four Core Object Types
1. **Blob**: Raw byte content of a file. Filenames, permissions, and timestamps are not stored here.
2. **Tree**: Equivalent to a Unix directory. Maps filenames and file mode bits (`100644`, `100755`, `040000`) to SHA-1 hashes of blobs or subtrees.
3. **Commit**: Contains a pointer to a root tree object, parent commit SHA-1s, author/committer identities, timestamps, and the commit message.
4. **Tag**: An annotated object pointing directly to a specific commit, carrying a GPG signature.

### 5.2 Storage Format on Disk
Every object is stored under `.git/objects/xx/yyyy...` where `xx` is the first 2 hex digits of the 40-character SHA-1 hash, and `yyyy...` is the remaining 38 characters:

$$\text{Object Header} = \text{"<type> <size>\0"}$$
$$\text{Storage on Disk} = \text{zlib\_deflate}(\text{Object Header} + \text{Raw Payload})$$

Because objects are keyed by the hash of their content:
- Git performs automatic deduplication across branches and directories.
- Any modification to a single character changes the blob SHA-1, which cascades up and changes the tree SHA-1, which changes the commit SHA-1. History is cryptographically unforgeable.

## 6. Packfiles and the Index: Engineering for Extreme Speed

Linus understood that loose objects would exhaust file inodes on POSIX filesystems. Git introduced **Packfiles** (`.pack` and `.idx`):
- Multiple loose objects are combined into a single packfile.
- Objects are delta-compressed against similar blobs (even across different files and revisions).
- A binary search index file (`.idx`) allows $O(\log N)$ random access to any object inside a multi-gigabyte packfile using `mmap()`.

### 6.1 The Staging Area (The Index)
The `.git/index` is a flat, binary cache containing sorted entries of pathnames, stat information (`ctime`, `mtime`, `dev`, `ino`, `size`), and the corresponding blob SHA-1.
When you run `git status`, Git performs a `stat()` syscall on files. If `size` and `mtime` match the index, Git knows without reading the file from disk that it is unmodified. This allows Git to scan hundreds of thousands of files in milliseconds.

## 7. The Legacy of Git

Git did not merely save Linux kernel development; it redefined global software engineering:
- Distributed collaboration eliminated the bottleneck of central code gatekeepers.
- It enabled GitHub, GitLab, and the open-source revolution of the 2010s and 2020s.
- Today, Git manages millions of repositories worldwide, powering software across every operating system, server, and cloud provider on Earth.
