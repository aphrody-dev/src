Défauts vérifiables. Les numéros de ligne sont ceux du fichier `prompt.md`. Je n'ai ni compilé ni exécuté les tests.

1. **`src/lib.rs` L473, `unwrap()` sur `partial_cmp` : panique possible.** `"x;q=NaN"` est accepté par `parse::<f64>()`. Le tri panique alors sur un en-tête HTTP fourni par le client, donc un déni de service. Correction : `b.0.total_cmp(&a.0)`, ou filtrer `q.is_finite()` et borner `q` à `[0,1]`.

2. **`src/lib.rs` L432-436, `match_locale` : le BCP47 est cassé.** Le tag est mis en minuscules. Si `supported` contient `"zh-CN"`, la comparaison passe par `eq_ignore_ascii_case`, donc l'exact fonctionne. En revanche `zh-TW` et `zh-Hans-CN` retombent sur `zh-CN` par la seule langue.
   - Le test L587-588 fige ce comportement : le chinois traditionnel reçoit du simplifié.
   - Il faut gérer le script (`Hant` ne doit pas correspondre à `CN`), ou retirer `zh-TW` du test et le documenter.
   - `split(['.', '@'])` est du format POSIX, pas du BCP47. Il n'a rien à faire dans la négociation HTTP.

3. **`src/lib.rs` L444-450, doublon dans `match_locale`.** Le `find` sur `base` est suivi d'un `or_else` qui fait presque la même chose. Seule la branche `or_else` est utile. Le premier `find` est mort : il ne gère que le cas où `supported` contient exactement `base`. Il faut le fusionner en un seul passage.

4. **`src/lib.rs` L345-350, `plural_category` : règles CLDR incorrectes.**
   - Le `int &&` ne s'applique qu'à `en` et `es`.
   - Pour `fr`, `(0.0..2.0).contains(&n)` rend `one` pour 1.5, ce que CLDR classe en `other` pour les entiers. Pour les décimaux, CLDR utilise `i = 0,1` avec `v = 0`.
   - `es` a aussi la catégorie `many` (1 000 000 et plus).
   - Les nombres négatifs ne sont pas traités : `-1` en `en` donne `other`. Intl donne `one` pour la valeur absolue.
   - Correction : utiliser `n.abs()`, le test de valeur entière et la règle `i = 0,1`.

5. **`src/lib.rs` L353-358, `num_text` : `v as i64` sature.** Pour `1e20` ou `NaN`, la sortie est fausse (`i64::MAX`, ou `0` pour `NaN`). Le commentaire L81-83 avoue l'écart avec `Intl.NumberFormat` (pas de groupement des milliers), mais le doc-comment du crate affirme « same message subset ». Correction : gérer les cas non finis et utiliser `{v}` pour les grandes valeurs. Idéalement, implémenter le groupement par locale ou rejeter explicitement.

6. **`src/lib.rs` L375-376, branche morte.** `Some(Arg::Num(v)) if *number` et `Some(Arg::Num(v))` produisent le même code. Soit `number` est inutile, soit le formatage devrait différer. Supprimer le champ ou implémenter la différence.

7. **`src/lib.rs` L409, `select` avec argument absent : `"undefined"`.** C'est une imitation de JavaScript, sans raison en Rust. Mieux vaut sauter la branche ou renvoyer une erreur, et être cohérent avec `Arg` manquant, qui rend `{name}` (L374).
