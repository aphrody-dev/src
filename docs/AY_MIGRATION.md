# One `ay`: migration of aphrody infra, yolo infra, yolo vps, yolo backend into the monorepo

Owner request (2026-11-12): merge "aphrody infra, yolo infra, yolo vps, yolo backend and src" into one
complete `ay` (`crates/ay`). This document holds the evidence-based inventory, the per-domain
production cutover, the fr2 rebuild checklist and the ordered plan. It was produced read-only.
Nothing on the hosts or in DNS was changed, except the one incident recorded in section 11.

This document extends the existing docs and does not repeat them:

- `docs/INFRA_MATRIX.md`: machines and accounts.
- `infra/deploy.toml`: node roles, set in 1e370c2.
- `docs/WORKSTATION_INVENTORY.md`: everything on the PC outside `C:\src`.
- `docs/LEGACY_AUDIT_AND_PURGE_REPORT.md`: per-repo assessment of `C:\src\var\legacy`.
- `docs/CONSOLIDATION_PLAN.md`: the workspace flattening.
- `apps/r2b/PLAN.md`: reverse-engineering and replica code (yolo-re, rea, replica).
- `apps/l2l/PLAN.md`: migration tooling (n2b, oxc, Bun plugins).

What those documents already decide is not planned again here.

Target node roles (owner, revised 2026-11-12):

- **usa** (`ssh prd`, 72.60.186.43, 2a02:4780:28:8e1e::1) runs all production. Every public DNS
  record points to usa.
- **fr1** (`ssh vps`, 51.77.147.152) does builds only: Chromium, AOSP, the Linux kernel, wasm and
  Steam game builds. Every serving unit there moves to usa or is deleted.
- **fr2** (`ssh cdn`, 51.255.162.6) is the CDN edge (caching in front of usa) and a test machine.
  It will be wiped and reinstalled.

Evidence was collected on 2026-11-12 between 07:00 and 08:30 UTC. Host commands: `systemctl cat`,
`ss -tlnp`, `docker system df`, `df`, `md5sum`, `git remote` and the nginx config files. External
sources: `gh repo list`, the Cloudflare DNS API (read-only, 184 records in 5 zones) and `curl` on
all 106 web hostnames. Env files are cited by path only. No secret value was read or printed.

## 1. Summary of findings

1. **Production runs on fr1, not usa.** Of the 106 web hostnames in aphrody.com, aphrody.app and
   rosegriffon.fr, 21 aphrody.app A records and 4 aphrody.com A records point to fr1. The 38
   aphrody.com CNAMEs follow the apex, which is an A record to fr1 (DNS-only). `api.aphrody.com`
   and `vps.aphrody.com` also carry fr1's IPv6 address. fr1 nginx serves aphrody.com and its
   subdomains from `aphrody-web` (:3000), `aphrody-app` (:3010), `aphrody-site` (:8083), store,
   downloads, chat and the fonts proxy, out of a `/opt/aphrody/monorepo` checkout. Separately,
   `infra/internal/providers/vps.go` still rejects every non-Google workload on usa. That
   contradicts `infra/deploy.toml` (`allow_non_google_workloads = true`) and the owner decision, so
   `ay deploy up` to usa fails today.
2. **70 of the 106 hostnames are already down with Cloudflare 526** (invalid origin certificate).
   The affected set: `aphrody.app`, `www.aphrody.app`, all 15 `app-*.aphrody.app`, the 15 `*craft`
   names, and 30 aphrody.com subdomains (search, docs, drive, mail, maps, ...). They are proxied,
   but no origin vhost on fr1 has a valid certificate for them. `omar.aphrody.com` and
   `desktop.aphrody.app` return 502. `rosegriffon.fr` returned 502 at 07:12 while its usa compose
   stack restarted and 200 at 08:20. On fr1, `rg-website` is `failed` and `rg-core` is `inactive`.
   DNS for rosegriffon already points to usa, so the fr1 rosegriffon vhosts are dead configuration.
3. **The `aphrody infra`, `yolo`, `backend` and `ovh` commands already exist** in a Rust multicall
   binary, `aphrody 1.0.0-canary`. It is 335 MB in `/usr/local/bin/aphrody` on fr1 and 331 MB in
   `~/.local/bin/aphrody` on fr2. It has 40 commands and also answers to the former binary names
   (`infra, ovh, yolo, kernel, host-service, ssh, wsl, backend, ...`). It was built from
   `aphrody-labs/bun-os`, **which no longer exists on GitHub (404)**. The 34,629-commit history
   survives only in host clones: fr1 `~/src/bun-os`, usa `/root/src/bun-os` (3.2 GB) and
   `/srv/yolo-fleet/wii-os`, and fr2 `~/src/bun-os`. The code survives byte-identical in
   `yolo-rs/yolo-backend` on GitHub, and without history in `C:\src\var\legacy\bunos`
   (gitignored). Crate sizes, in lines:

4. **All three nodes run the same yolo stack.** On usa, fr1 and fr2 the md5 hashes of
   `/opt/yolo-vps/agent/*.ts`, `/opt/yolo-git-sync/auto-deploy.ts` and
   `/opt/yolo-cf/bin/yolo-cf-gateway` match. Each node runs `yolo-vps-agent`, `yolo-auto-deploy`,
   `yolo-ram-cache`, `yolo-cf-{garage,rqlite,workerd,gateway}`, the `yolo-repo-purge` timer,
   `aphrody-ai`, `hermes-agent` and `opencode-agent`. That is 12 duplicated units on 3 nodes, with
   about 0.9 GB of `/opt/yolo-cf` binaries per node.
5. **The yolo-cf "self-hosted Cloudflare" has no clients.** The only established connections to
   ports 17080-17903 were garage RPC between the three peers. No nginx route on any node points at
   it. It duplicates real Cloudflare, which is now reachable with a verified API token. rqlite runs
   with `-bootstrap-expect=3`, so retire it on all three nodes at once.
6. **`yolo-ram-cache` exists to consume RAM.** Its own header says it targets "78% productive RAM
   utilization". It fallocates `/dev/shm` slabs of 12 GB on fr1, 8 GB on usa and 5 GB on fr2.
   Measured cgroup memory: 27.9 GB on fr1 (45 GiB host, load average 52 on 12 vCPU), 4.9 GB on usa
   and 4.5 GB on fr2 (11 GiB host).
7. **`yolo-auto-deploy` is a second deploy path that nobody reviews.** It runs as root on every
   node: every 60 s it resets checkouts to `origin/main`, builds them and reloads services. That
   means it builds on production (usa) and on the edge (fr2), outside `ay deploy`.
8. **Disk pressure comes from duplicate clones.**
   - fr2: `/` is 90% full and `/home/ubuntu` holds 59 GB, mostly clones: rosegriffon 4x, yolo-web
     3x, yolo-ui 2x, yolo-os 3x, shenron 3x, plus bun-os. fr2 also serves fr1's build cache
     (`/srv/yolo_build_cache`, over sshfs).
   - fr1: Docker can reclaim 18.0 GB of volumes (25 volumes, 98% unused), 17.98 GB of build cache
     and 21.9 GB of images.
   - usa: 12.0 GB of build cache is reclaimable. Four rosegriffon clones take about 8.7 GB and
     `/srv/yolo-fleet` 5.7 GB.
9. **AI daemons run outside `packages/ai-os`.** These run as root on several nodes:
   - `aphrody-ai` ("24/7 autonomous supervisor")
   - `hermes-agent` (secret audits and auto-commit)
   - `opencode-agent`
   - `yolo-app-server` (usa Docker :1338)
   - `aphrody-a2a`
   - `llama-server` (usa :8799)

   Repository policy makes `packages/ai-os` the only owner of AI code, so none of these belong in
   `ay`.

10. **GitHub sprawl.** `yolo-rs` has 66 repositories: 45 are archived forks or consolidations and
    19 are live `yolo-*` repos (about 1.4 GB). Only three hold infra code that the hosts run:
    `yolo-vps` (879 lines of Rust plus the Bun agents and units), `yolo-cloudflare` (Pingora
    gateway and cluster scripts) and `yolo-backend` (the copy of the bun-os infra crates). Local
    clones of all of them sit in `C:\src\var\legacy` (7.4 GB, gitignored).

The production code on fr1 is pushed. `/opt/aphrody/monorepo` is at `aphrody-dev/src` 7d33be3,
which is 29 commits behind the local `main`. Its `apps/aphrody` is at 38935c3, which is on
`aphrody-dev/aphrody` `origin/main`. Its `apps/aphrody-app` is at b378ca3, on
`aphrody-dev/aphrody-app` `origin/dev` but not `main`. Both repos are archived and merged into
`apps/` here. Release directories under `/home/ubuntu/apps/*` are not git; their sources are listed
per row in section 5.

Community products (not Aphrody): `apps/shenron` (dragonballfr.com, `dbfr.aphrody.com`) and
`apps/rosegriffon` (rosegriffon.fr). They follow the same node rules and are never branded or merged
as Aphrody features.

## 5. Production cutover to usa, per domain

**Method, the same for every row:**

1. Build the artifact from `C:\src` at a commit that contains the code fr1 runs. `apps/aphrody`
   and `apps/aphrody-app` hold the merged history of the archived repos.
2. On usa, install a systemd unit (`aphrody-<svc>@blue`) bound to `127.0.0.1:<blue port>` and run
   it as a dedicated non-root user, not root.
3. Install a TLS certificate before touching DNS. Use a Cloudflare Origin CA certificate for
   `*.aphrody.com`, `aphrody.com`, `*.aphrody.app` and `aphrody.app` (proxied records), or Let's
   Encrypt through DNS-01 with `CLOUDFLARE_API_TOKEN` (DNS-only records). HTTP-01 does not work
   before DNS moves.
4. Add the nginx vhost on usa and check it with
   `curl --resolve <host>:443:72.60.186.43 https://<host>/health` while DNS still points to fr1.
5. Switch the Cloudflare record. A proxied record changes within seconds; a DNS-only record follows
   TTL `auto` (300 s). Then watch the fr1 nginx access log drain to zero.
6. Keep the fr1 unit running for 7 days, then stop and disable it.

**Rollback:** set the record content back to `51.77.147.152`.
