# Install and update

How `ay`, the toolchain around it, and published wasm/CDN assets are installed and kept current on
the workstation and on the three hosts (`usa` production, `fr1` builds and storage, `fr2` CDN, cron
and sync; see `docs/INFRA_MATRIX.md`).

| Piece | Where | Command |
|---|---|---|
| `ay` releases | `dist-workspace.toml`, `.github/workflows/release.yml` | tag `v<version>` |
| `ay` self-update | `crates/ay/src/self_update.rs` (axoupdater) | `ay self-update [--check] [--version X]` |
| Toolchain manifest | `tools.toml` | `ay up --list` |
| Toolchain installer | `crates/up` (`aphrody-up`) | `ay up`, `ay up --check`, `ay up <tool>...` |
| Provider wiring | `crates/up/src/setup.rs` | `ay up --setup` |
| Workstation bootstrap | `crates/up/src/bootstrap.rs`, `[[file]]` / `[[link]]` / `[[step]]` in `tools.toml` | `ay up --bootstrap` |
| Host schedule | `infra/generated/systemd/ay-up.{service,timer}` | daily, user units |
| Asset manifests | `crates/up/src/assets.rs` | `ay up --assets <dir> [--release <label>]` |

## 1. Releasing `ay` (dist)

`ay` is the package `aphrody` (crates/ay). It is the only workspace member dist builds:
`dist-workspace.toml` sets `dist = false` for everyone and `crates/ay/Cargo.toml` opts back in with
`[package.metadata.dist] dist = true`. Targets: `x86_64-pc-windows-msvc`,
`x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl`, `x86_64-apple-darwin`,
`aarch64-apple-darwin`. Installers: shell and PowerShell, both installing into `~/.local/bin`
(`install-path`), the same directory `ay up` manages. Builds use `[profile.dist]` in the root
`Cargo.toml`, which inherits `release` (fat LTO, one codegen unit, abort, stripped).

Release steps:

1. Bump `[workspace.package] version` in the root `Cargo.toml` and the `ay` pin in `tools.toml`.
2. `dist plan` must list `aphrody-<target>.{zip,tar.xz}` with `.sha256` files and both installers.
3. Push the tag `v<version>`. `.github/workflows/release.yml` builds every target, uploads the
   archives, `sha256.sum`, `source.tar.gz` and `aphrody-installer.{sh,ps1}` to a GitHub Release on
   `aphrody-dev/src`.

The workflow is generated by `dist generate` with one manual patch: every `actions/checkout` step
gets `token: ${{ secrets.SUBMODULES_TOKEN || github.token }}`, because `crates/bench`,
`crates/ring3-agent`, `crates/rust-stack` and some `apps/*` are private submodules that the
default `GITHUB_TOKEN` cannot read (and the workspace glob `crates/*` needs them). Create the
secret once with a read-only token for `aphrody-dev` and `aphrody-labs`
(`gh secret set SUBMODULES_TOKEN -R aphrody-dev/src`). `allow-dirty = ["ci"]` keeps `dist plan`
from rejecting the patch; re-apply it after any `dist generate`.

First install on a fresh machine (public release assets):

```sh
curl --proto '=https' --tlsv1.2 -LsSf https://github.com/aphrody-dev/src/releases/latest/download/aphrody-installer.sh | sh
```

```powershell
irm https://github.com/aphrody-dev/src/releases/latest/download/aphrody-installer.ps1 | iex
```

While `aphrody-dev/src` is private, release assets need a token: either copy a `ay` built with
`ay build --target linux-musl --release`, or download with `gh release download v<version> -R aphrody-dev/src`.

## 2. `ay self-update`

`ay self-update` embeds axoupdater (blocking API). With a dist install receipt it reuses the
receipt's source and install prefix; without one (a binary built from source or placed by `ay up`)
it targets GitHub Releases of `aphrody-dev/src`, app `aphrody`, the current version from the
binary, and the directory of the running executable. It downloads the release's
`aphrody-installer.{sh,ps1}` and runs it with the install directory forced, so the result is the
same as a fresh install. `GH_TOKEN` / `GITHUB_TOKEN` are passed to the release lookup.

- `ay self-update --check`: exit 0 when current, 1 when a newer release exists.
- `ay self-update --version 0.3.0`: install that version (also downgrades).

Limitation: the dist installer script downloads its archive anonymously, so on a private repo the
lookup succeeds and the install fails. `ay up ay` covers that case: it downloads the pinned
release through the GitHub API with the token.

## 3. `ay up` and `tools.toml`

`tools.toml` lists every tool with a pinned version, the executables it provides, a version probe
and one source:

| Source | Used for | Install |
|---|---|---|
| `github` | ay, bun, gh, ovhcloud, coreutils, ripgrep, just, cargo-zigbuild, dist | release asset per platform, executables copied into `bin_dir` |
| `url` | gcloud, zig | direct archive; `layout = "tree"` unpacks under `tools_dir/<name>/<version>` and links `bin` entries into `bin_dir` |
| `bun` | wrangler, hostinger-api-mcp | `bun add --global <package>@<version>` (Bun's own `~/.bun`) |
| `installer` | rustup | `rustup-init -y --no-modify-path --default-toolchain none`; an existing rustup runs `rustup self update` |
| `ubi` | fd, dust, bat, delta, sd, hyperfine, tokei, watchexec, zoxide, eza, xh, yq, jj, sccache, uv, caddy, cloudflared, rclone, cargo-binstall, cargo-nextest, gitoxide | the `ubi` crate picks the asset for the OS/arch at the pinned tag and installs the executable into `bin_dir`; `matching.<os>` breaks ties (`msvc`, `max-pure`) |

Two installers coexist on purpose. `github` / `url` entries name the exact asset per platform and
verify sha256; they cover the tools that matter for builds, deploys and the hosts. `ubi` entries
need only `repo` and a tag, which keeps 21 general CLI tools to a few lines each, but ubi 0.13
verifies no checksum (the install line says so). Move a tool from `ubi` to `github` when its
integrity matters. The ubi pins match what the workstation already has, so `ay up` adds no second
copy next to the winget or cargo one.

Versions with `lock = "<key>"` (bun, just, zig) come from `src.lock.json` `toolchains.<key>` when
the repository is present. Manifest lookup order: `--manifest`, `$AY_TOOLS_MANIFEST`,
`<repo>/tools.toml` (repo found through `$SRC_ROOT` or the nearest `src.lock.json`), then the copy
embedded in the binary at build time, which is what hosts without a checkout use.

States: `ok`, `ahead` (newer than the pin, left alone), `outdated`, `missing`, `unknown` (version
unreadable), `n/a` (no asset for this platform). `ay up --check` prints the table and exits 1 when
any tool is `missing` or `outdated`. `ay up` acts on exactly those, then probes again;
`--dry-run` prints the download URLs instead.

Rules the installer enforces:

- Writes only under the user's home: `bin_dir` (default `~/.local/bin`, `AY_BIN_DIR` overrides),
  `tools_dir` (`~/.local/share/ay/tools`), Bun's global directory, rustup's `~/.cargo`.
  Destinations under `%WINDIR%` (including `C:\Windows\System32`), `Program Files`, `/usr`, `/bin`,
  `/sbin`, `/lib`, `/etc` and `/opt` are refused.
- A tool found outside `bin_dir` at the right version is left where it is (winget, Program Files,
  `~/.cargo/bin`). An outdated one gets a fresh copy in `bin_dir`, which must come first on `PATH`.
- Binary tools are probed as real executables (`rg.exe`, never an unrelated `rg.cmd` shim).
- sha256 is verified whenever upstream publishes it: release checksum files (`SHA256SUMS`,
  `SHASUMS256.txt`, `gh_<v>_checksums.txt`), per-asset `.sha256`, `{url}.sha256` (rustup), or
  hashes pinned in `tools.toml` (zig, from `ziglang.org/download/index.json`). coreutils and
  gcloud publish none; the output says `no checksum published`.
- Running executables are replaced by rename (`.ay-old`), so `ay up` can update `ay.exe` itself.
- `ay up --check` prints `note:` lines for duplicates (the same tool at several PATH entries, e.g.
  bun from winget and `~/.bun/bin`) and shadows (a same-name shim winning for cmd/PowerShell, e.g.
  `~/.local/bin/rg.cmd` in front of ripgrep). Notes never change the exit code.
- HTTP is ureq 3 (rustls on ring; `Authorization` is dropped on redirects); archives are read with
  `zip` 9, `tar` + `flate2`, and `lzma-rust2` (xz), all pure Rust. The `ubi` path brings reqwest
  and tokio (shared with axoupdater) plus ubi's own `xz2` and `zstd` C builds (cc only, no cmake).

Adding a tool: append a `[[tool]]` with assets for the five platform keys
(`windows-x86_64`, `linux-x86_64`, `linux-aarch64`, `macos-x86_64`, `macos-aarch64`) and a
checksum source (`cargo test -p aphrody-up` fails if a `github`/`url` tool misses a platform), or
a `source = "ubi"` entry with `repo` and the tag template.

## 4. Workstation bootstrap (`ay up --bootstrap`) and the install scripts

`scripts/install.ps1` and `scripts/install.sh` are ten-line bootstraps: they build `ay` once (`cargo install --path crates/ay`) and run `ay up --bootstrap`. Every step the former root scripts
performed has a declarative equivalent in `tools.toml`, applied by `ay up --bootstrap` (tools first,
then the items below, then `ay doctor`). `ay up --check` lists the items with their state (`ok`,
`differs`, `missing`) without counting them in the exit code.

| install.ps1 / install.sh step | `ay up` equivalent |
|---|---|
| `Ensure-Tool` sccache, just, jj, cargo-binstall, cargo-nextest, gix (winget / cargo binstall) | `[[tool]]` entries (`ubi` or `github`), no compile |
| `~/.local/bin` on the user PATH | the dist installer adds it on first install; `ay up` writes nowhere else |
| write `~/.cargo/config.toml` (sccache wrapper, `ay` alias, target-cpu=native) | `[[file]] cargo-config` per OS, created only when missing |
| write the jj config (`%APPDATA%/jj`, `~/.config/jj`) | `[[file]] jj-config` at `{config}/jj/config.toml` |
| clone missing repositories from `src.lock.json` | built in: missing `repositories` entries with an https/ssh URL are cloned `--depth=1 --filter=blob:none` |
| `cargo install --path crates/ay` | the `ay` tool entry (dist release), then `ay self-update` |
| `go build ./cmd/src-deploy` | `[[step]] src-deploy` (runs when `infra/go.mod` exists and the binary is missing) |
| `bun build --compile packages/ai-triad` | `[[step]] triad` |
| `frg.cmd` / bash `frg` shim | `[[step]] frg`: an AOT `bun build --compile` binary instead of a shim |
| `.claude/skills` junction or symlink | `[[link]] claude-skills` (junction on Windows, symlink elsewhere) |
| `ay doctor` | run at the end of `--bootstrap` |
| `cargo build --release` in `crates/rust-stack` | dropped: it is a root workspace member (`cargo build -p rust-stack`) |

Steps run with `RUSTC_WRAPPER` empty: building through sccache crashes rustc on the workstation
(the same reason `just install-ay` needs `RUSTC_WRAPPER=` today).

Once a public `ay` release exists, both scripts shrink to a bootstrap of about ten lines:

```powershell
# install.ps1 (target)
$ErrorActionPreference = "Stop"
irm https://github.com/aphrody-dev/src/releases/latest/download/aphrody-installer.ps1 | iex
$env:PATH = "$env:USERPROFILE/.local/bin;$env:PATH"
$env:SRC_ROOT = $PSScriptRoot
ay up --bootstrap
ay up --setup
```

```sh
# install.sh (target)
set -eu
curl --proto '=https' --tlsv1.2 -LsSf https://github.com/aphrody-dev/src/releases/latest/download/aphrody-installer.sh | sh
export PATH="$HOME/.local/bin:$PATH"
SRC_ROOT="$(cd "$(dirname "$0")" && pwd)" ay up --bootstrap
ay up --setup || true
```

## 5. `ay up --setup`

Non-interactive provider wiring. Credentials are read from the process environment first, then
`<repo>/.env` (dotenvy; the process environment is not modified). Values are never printed: they
reach child processes through their environment or stdin, and every printed line is scrubbed of
credential values.

| Provider | Needs | Check | Wiring |
|---|---|---|---|
| GitHub | `GH_TOKEN` or `GITHUB_TOKEN` | `gh auth status` against stored credentials | if not logged in, `gh auth login --with-token` from stdin |
| Cloudflare | `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID` | `wrangler whoami` with both in its environment | env only (wrangler reads them per run) |
| Google Cloud | an active gcloud account | `gcloud config get-value account` | if none and `GOOGLE_APPLICATION_CREDENTIALS` is a file, `gcloud auth activate-service-account` |
| OVHcloud | `~/.ovh.conf` | `ovhcloud account get` | none (created by `ovhcloud login`) |
| Hostinger | `HOSTINGER_API_TOKEN` | `GET https://developers.hostinger.com/api/vps/v1/virtual-machines` returns 200 | none |

The table shows the provider, which credential names were found, `ok`/`FAIL` and a masked detail
(`a***@domain` for accounts). Exit 1 when any provider fails.

## 6. Hosts: daily `ay up`

`infra/generated/systemd/ay-up.service` and `ay-up.timer` are **user** units, so nothing runs as
root on fr1/fr2 and `%h` resolves to the deploy user's home. They are not deployed by any tool;
install them by hand on each host:

```sh
mkdir -p ~/.config/systemd/user ~/.config/ay
cp ay-up.service ay-up.timer ~/.config/systemd/user/
printf 'GH_TOKEN=...\n' > ~/.config/ay/env && chmod 600 ~/.config/ay/env   # only for private releases
loginctl enable-linger "$USER"
systemctl --user daemon-reload
systemctl --user enable --now ay-up.timer
systemctl --user list-timers ay-up.timer
journalctl --user -u ay-up.service
```

Each run (daily, randomized within an hour, catching up after downtime): `ay self-update` first
(failure ignored), then `ay up`. The order matters: the embedded `tools.toml` travels with the
binary, so a new `ay` release is how new tool pins reach hosts. A host with a checkout can follow
the repository instead by setting `SRC_ROOT=/home/ubuntu/src` in `~/.config/ay/env`.

| Host | User | Notes |
|---|---|---|
| `usa` (`ssh prd`) | root | production; `ay up --setup` with `HOSTINGER_API_TOKEN` checks the API |
| `fr1` (`ssh vps`) | ubuntu | builds: rustup, zig, cargo-zigbuild, dist matter most |
| `fr2` (`ssh cdn`) | ubuntu | CDN, cron and sync: wrangler and gcloud matter most |

The aarch64 Linux `cargo-zigbuild` asset is a glibc build; the hosts are x86_64 Ubuntu.

## 7. Wasm and CDN assets on R2

Published files are content-addressed and never overwritten; one small manifest per release says
which objects are current.

1. Build (for wasm: `ay build -t wasm32 --release`, then `wasm-bindgen` into a `pkg/` directory).
2. `ay up --assets <dir> --release <version-or-commit> > manifest.json` hashes every file and
   prints, per logical path, the immutable key `<stem>.<sha256[0..12]>.<ext>`, the full sha256,
   size and content type (`application/wasm` for `.wasm`). Output is sorted and deterministic.
3. Upload each asset under its key once (keys that exist are skipped, so a release only uploads
   what changed), with `Cache-Control: public, max-age=31536000, immutable`:
   `wrangler r2 object put <bucket>/<key> --file <dir>/<logical> --content-type <type> --cache-control "public, max-age=31536000, immutable"`.
4. Upload `manifest.json` last to `<bucket>/<app>/manifest.json` (short `max-age`, e.g. 60 s) and a
   copy to `<bucket>/<app>/releases/<release>.json` for rollback. Rolling back is re-uploading an
   older `releases/<release>.json` as `manifest.json`.
5. Pages and loaders resolve logical names through the manifest, so a deploy is atomic for clients:
   they see either the old manifest and old objects, or the new manifest and new objects.

Buckets per service are in `infra/deploy.toml` (`r2_bucket`); the CDN origin is `fr2`. Garbage
collection of keys no longer referenced by any `releases/*.json` is a later step and not
implemented. Only step 2 is implemented in `ay` today (`crates/up/src/assets.rs`, tested); upload
stays with `wrangler` until the deploy engine takes it over.
